# Cerebras WSE Profiling Architecture: What's Available and How It Helps Agents

## Overview

The Cerebras simulator and SDK provide 7 layers of profiling data, from aggregate
cycle counts to per-PE instruction-level traces. Currently the xkernel agent uses
only Layer 1 (TSC cycles). This document describes what each layer contains and
how it could improve agent reasoning for better CSL optimization.

## Layer 1: TSC Timing (ACTIVE — primary metric)

**Source:** `run.py` stdout → `cycles_send = N cycles`
**What it tells the agent:** Total elapsed cycles for the timed compute window.
**Limitation:** Single scalar — no breakdown of WHERE cycles are spent.

## Layer 2: sim.log Aggregate Stats (IMPLEMENTED — in profile_csl.py)

**Source:** `sim.log` in the staged bundle (auto-generated by simulator)

**What it contains:**
```
@51828 CTF Stats: num_stalls_       =            0
@51828 CTF Stats: num_wavelets      =         2705
@51828 CTF Stats: num_inst_dispatch =        21305
@51828 CTF Stats: num_inst_pipe     =        67364
```

**What it tells the agent:**
- `num_stalls / num_inst_dispatch` = stall ratio → is the kernel stall-bound?
- `num_wavelets / num_inst_dispatch` = wavelet density → is it fabric-heavy?
- `idle_cycles_at_end` → how long are PEs idle after compute finishes?
- Grid topology: `dimX=9, dimY=4` → 9×4 fabric, 18 hw tiles, 4 io tiles

**How it helps:** The bottleneck classification (compute-bound / fabric-bound /
stall-bound) directs the optimizer to the right family of optimization angles.

## Layer 3: CTF Binary Traces (AVAILABLE — not yet parsed)

**Source:** `simfab_traces/stream0` (binary CTF format, 4-10 MB per run)

**What it contains (7 event types):**

### 3a. `backpressure_trace_entry`
Fields: `cycle`, `tile_index`, `back_pressure`, `color`

**What it tells the agent:** Per-PE, per-cycle back-pressure status on each fabric
color. Identifies congestion hotspots — which PE and which color is the bottleneck.

**Agent insight:** "PE(2,1) has persistent back-pressure on color 8 (the NS halo
exchange color) starting at cycle 5000 — the south neighbor sends faster than this
PE can consume. Add a FIFO or overlap receive with compute."

### 3b. `hwm_dispatch_trace_entry`
Fields: `cycle`, `tile_index`, `uid`, `opcode`

**What it tells the agent:** Per-PE instruction dispatch timeline. Shows exactly
WHICH instruction is executing at each cycle, with a unique ID for tracing.

**Agent insight:** "PE(1,1) dispatches 400 @fmovs instructions but only 200 @fmacs
— the data movement dominates compute. Use DSD offset chaining to reduce @fmovs."

### 3c. `hwm_pipe_trace_entry`
Fields: `cycle`, `tile_index`, `uid`, `opcode`

**What it tells the agent:** Pipeline-level trace showing multi-cycle instructions
in the execution pipeline. Distinguishes single-cycle dispatches from multi-cycle
pipeline operations.

### 3d. `wavelet_trace_entry`
Fields: `cycle`, `ident`, `tile_index`, `color`, `direction`, `data`

**What it tells the agent:** Per-wavelet trace — tracks individual wavelets as
they flow through the fabric. The `ident` field links send and receive events.

**Agent insight:** "Wavelet #42 sent from PE(0,1) at cycle 3000, arrived at PE(1,1)
at cycle 3002 (2-cycle hop). But wavelet #43 arrived at cycle 3050 (48-cycle delay)
— congestion on color 9 between cycles 3002-3050."

### 3e. `debug_counters_wavelet`
Fields: `PE_x`, `PE_y`, `color`, `wavelet_count`

**What it tells the agent:** Per-PE, per-color wavelet count summary. Shows traffic
distribution across the mesh.

### 3f. `switch_pos_trace_entry`
Fields: `cycle`, `tile_index`, `color`, `direction`, `position`

**What it tells the agent:** Fabric switch position changes — when and where routing
configurations change during execution.

### 3g. `wavelet_entry`
Fields: `PE_x`, `PE_y`, `color`, `direction`, `data`

**What it tells the agent:** Wavelet landing events — when a wavelet arrives at a PE.

## Layer 4: ELF Symbol/Task Analysis (AVAILABLE — partially used)

**Source:** `cs_readelf` or `debug_util.ELFMemory` on compiled ELF files

**What it contains:**
- Per-PE memory usage (section sizes)
- Symbol table: variable names, addresses, sizes
- Task table: mapped task functions with their instruction addresses
- Fabric dimensions and PE coordinates

**What it tells the agent:**
- Memory pressure: "PE(4,1) uses 44KB/48KB SRAM — near overflow"
- Function sizes: "f_compute is 400 instructions, f_send is 50 — compute dominates"
- Data layout: "Array A occupies 32KB, leaving 16KB for everything else"

## Layer 5: debug_util Post-Mortem (AVAILABLE — not yet used)

**Source:** `debug_util.debug_util(dirname)` in the SDK container

**What it provides:**
- `get_symbol(col, row, name, dtype)` — read any PE's memory post-simulation
- `get_symbol_rect(rect, name, dtype)` — read a rectangle of PEs
- `read_trace(col, row, key)` — read `<debug>` library traces

**What it tells the agent:** Actual runtime values from any PE — useful for
verifying correctness and understanding data distribution across the mesh.

## What Would Help Agents Most (Ranked)

### Priority 1: Per-PE Compute Utilization (from dispatch traces)

Parse `hwm_dispatch_trace_entry` events to compute:
```
for each PE:
    compute_cycles = count(opcodes in {fmacs, fadds, fmuls, fmovs, ...})
    idle_cycles = total_cycles - compute_cycles
    utilization = compute_cycles / total_cycles
```

**Agent prompt injection:** "PE(0,0): 85% utilized (compute-bound), PE(1,1): 30%
utilized (idle 70% — waiting on fabric). The bottleneck is PE(1,1)'s receive path."

### Priority 2: Back-Pressure Heatmap (from backpressure traces)

Parse `backpressure_trace_entry` to build a per-PE, per-color congestion map:
```
for each (PE, color):
    bp_cycles = count(back_pressure > 0)
    bp_fraction = bp_cycles / total_cycles
```

**Agent prompt injection:** "Color 8 (halo exchange) has 40% back-pressure on
PE(1,1) but 0% on PE(0,0) — the south→north data path is congested. Restructure
the halo send ordering or add async overlap."

### Priority 3: Wavelet Flow Analysis (from wavelet traces)

Parse `wavelet_trace_entry` to compute inter-PE communication latency:
```
for each wavelet ident:
    send_cycle = min(cycle where tile_index == sender)
    recv_cycle = max(cycle where tile_index == receiver)
    latency = recv_cycle - send_cycle
```

**Agent prompt injection:** "Average wavelet latency: 2 cycles (nearest-neighbor).
But 15% of wavelets have >10 cycle latency — fabric congestion during peak exchange."

## Integration Plan

### Phase 1 (done): sim.log aggregates → bottleneck label
Already in `profile_csl.py`: stall ratio, wavelet density, classification.

### Phase 2 (next): CTF dispatch trace → per-PE utilization
Requires a CTF parser (Python struct-based, since babeltrace2 not available).
Parse `stream0` binary using the `metadata` schema definitions.

### Phase 3 (future): Back-pressure + wavelet flow → congestion map
Full fabric analysis for multi-PE optimization guidance.
