> for these kernels come from re-instrumented bundles via `hw_replay.py`.


Generated by `code_translation/aggregate_hw_vs_sim.py`.

## Method

Each row is ONE bundle, ported to SDK 2.10 once, then compiled and run
**both** ways through the same appliance client and driven by the
kernel's **own `run.py`**. The host sequence is therefore identical on
both arms and the `f_enable_timer` launch cannot go missing on one side
-- which is how the July 2026 attempt produced sub-100-cycle readings.
Both arms are checked for the SUCCESS marker and screened against the
same 100-cycle dead-timer floor.

| column | meaning |
|---|---|
| `sweep_sim` | SDK 1.4.0 local simulator -- what every sweep reports |
| `sim_2.10` | SDK 2.10 appliance simulator, same bundle |
| `hw` | real WSE-3 silicon, same bundle |
| `hw/sim` | hardware cost relative to simulator (>1 = hardware slower) |
| `port` | `sim_2.10 / sweep_sim`, the SDK-version + port delta |

### Does the gap scale with kernel size?

If the hardware penalty were a fixed per-launch overhead, the
*relative* gap would shrink as kernels get longer.
