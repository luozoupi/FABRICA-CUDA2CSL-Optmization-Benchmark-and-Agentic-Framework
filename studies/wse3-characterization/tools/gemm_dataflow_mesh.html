Across the mesh, from host to host

Step through a whole run, from where the data comes from to where the result is checked. Each PE is drawn as what it is: a router, a ramp into its core, and the core's SRAM. Inside a router every line is one route, rx port → tx port, as @set_color_config states it. Between routers, each arrow is one hop on one link, labelled with its colour and hop number. On the ramp, every tap passes a hardware queue (OQ out, IQ in). In SRAM, each buffer is shown at its compiled address, with the role the trace gives it in that phase. MeshGEMM double-buffers X and W in SRAM; MeshGEMV adds straight from the input queue. Tap any buffer to open its numbers from the run the host checked.

The same verified values in 3D, one layer per step with every value as a cube: open the WebGL view ↗

This tab follows the manner of qin00162/Cerebras (profiling/animate_native.py): one frame per simulator cycle on the 4 × 4 physical grid, with transfers drawn per physical hop as batch envelopes from the first upstream observation to the last downstream arrival, and the instructions each PE dispatched in that cycle tagged underneath it. The instance is a new traced run of the unmodified MeshGEMM at its smallest faithful size: X and W 8 × 8 with small integers, 2 × 2 tiles on 16 PEs (P = 2 is not possible: the folded two-hop ring is defined for P ≥ 3), one checked repeat, from the first host word to the last C word. Each PE is a pie: the left half is the X tile it holds, the right half the W tile, with the same darkness for the same k-block, so a matching pair reads as a symmetric pie; the centre fills as C accumulates. Counters show how long each tile has been on the PE and what it is doing (⚙ computing, ↗ being sent, · resident). Click a PE to zoom in: the two tiles' places in X and W, their values, and C so far at that cycle.

    The skew runs at the start of every repeat. In all 7 repeats of the trace the order on every PE is skew → C cleared → first FMACH, and each PE sends the same 256 skew packets and issues the same 1,024 FMACHs. The skew's pointer swaps, however, depend on x_shift_step. That counter is set only by init_task and counts down during the skew, so later repeats swap differently.
    
  
    Identified by content, every tile multiplied in every repeat is one of the verified tiles, but X's and W's k-blocks match on all 64 PE-steps only in repeat 1, the run the host reads back and checks. Repeat 2 is the timing run's warm-up: init_task reset the counter, but X had already been skewed once, so it matches on 32 of 64. Repeats 3–7 match on 16 of 64. Timing is unaffected: the instruction stream and traffic are identical, and consecutive repeats start 9,663–9,692 cycles apart. The timed repeats' values, though, are not X·W. The device launcher uses the same pattern (1 checked repeat, then 5 + 50 timed); that is not checked on silicon here.
